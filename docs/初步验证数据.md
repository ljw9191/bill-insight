# 初步验证数据（2026-11-13 实测）

本文件记录初赛提交所需的量化验证结果，全部由仓库内脚本 `scripts/measure-metrics.ts`
对可复核素材实测生成，未做任何估算或补造。复现命令：

```bash
npx vite-node scripts/measure-metrics.ts
```

运行环境：Windows 11 / Node.js 22 / Tesseract.js 6 / 本地 `chi_sim` 模型（2.4 MB）/ 单线程识别。

## 一、 OCR 识别准确率抽样

素材：`public/samples/wechat-ocr-demo.png`（微信支付账单详情，1047×1318，含金额、状态、商户、说明、时间、支付方式、交易单号）。

| 指标 | 结果 | 说明 |
|---|---|---|
| 字符错误率 CER | 2.2% | 与人工转录全文逐字比对，Levenshtein 编辑距离 / 标注总字数 |
| 字符准确率 | 97.8% | 1 - CER |
| 单张识别耗时 | 389 ms | 本地 CPU，单线程，不上传图片 |
| 字段级准确率 | 80%（4/5） | 日期、收支方向、商户、分类正确；金额错误 |

逐字段核对：

| 字段 | 人工标注 | OCR + 解析结果 | 结论 |
|---|---|---|---|
| 日期 | 2026-11-08 | 2026-11-08 | 正确 |
| 收支方向 | 支出 | 支出 | 正确 |
| 金额 | 186.50 | 186.20 | 错误（末位数字 5 被识别为 2） |
| 商户 | 海底捞火锅 | 海底捞火锅 | 正确 |
| 分类 | 餐饮 | 餐饮（置信度 0.84） | 正确 |

识别原文片段：`支付金额 / 半 186.20`（`¥` 被识别为“半”），说明：

1. 当前 `chi_sim` 快速模型在符号与相似数字上仍有误差，**金额必须允许人工修改**；
2. 也验证了系统的设计前提——OCR 结果只进入可编辑预览，不直接入账；
3. 改进方向明确：金额区域单独裁剪放大、数字白名单、符号预处理。

## 二、 内置分类规则命中与一致率

素材：与 `src/lib/demo.ts` 一致的 18 条标注账单（商户 + 备注），按真实分类入口 `classifyBill()` 计算。

| 指标 | 结果 |
|---|---|
| 样本数 | 18 |
| 规则命中率（置信度 ≥ 0.72） | 94.4%（17/18） |
| 分类一致率（与人工标注一致） | 94.4%（17/18） |

未命中样例：`公共交通 / 上月交通汇总` → 判为「其他支出」，置信度 0.3。
该样例没有套用内置的「交通」分类，而是**如实降到低置信度并交给用户核对**，说明低置信度暴露机制生效，不是静默给出错误结论。

## 三、 反馈反哺机制验证

素材：3 条不含内置关键词的构造商户（明确标注为构造用例，仅用于验证机制，不计入准确率统计）。

| 阶段 | 命中率 | 一致率 |
|---|---|---|
| 修正前（仅内置规则） | 66.7%（2/3） | 66.7% |
| 用户修正 3 条、生成个人规则后 | 100%（3/3） | 100% |

结论：一次修正即可沉淀为个人规则，并在后续同类账单上稳定命中，符合赛题要求的「用户修正反馈」闭环。

## 四、 当前验证的边界

- OCR 抽样目前只覆盖 1 张样例单据，样本量偏小；真实手机截图（不同分辨率、反光、深色模式）需要继续补样。
- 分类命中率基于演示标注集，不代表任意真实账单的分布。
- 上述两项均会在决赛前用真实账单补足样本，并在文档中同步更新。
